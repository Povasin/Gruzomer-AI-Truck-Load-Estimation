Решаемая проблема
Контроль загрузки транспорта по фотографиям требует ручной работы. Руководителям объектов сортировки, транспортных подразделений и логистики Почты России нужно понимать, насколько заполнен кузов, выявлять недогруженные автомобили и сопоставлять фактическую загрузку с нормативными отчётами.

Автоматическая оценка может сократить ручную проверку фотографий, помочь анализировать перевозки и выбирать транспорт подходящей вместимости.

Задача
Разработайте работающий MVP сервиса, который принимает фотографию грузового отсека и номер перевозки, определяет загрузку в процентах, сохраняет результат и возвращает его через API.

Целевая величина — экспертная оценка заполнения кузова по размещённым объектам, условно по занятой площади пола. Процент загрузки находится в диапазоне от 0 до 100. Оценка массы груза и доли использованной грузоподъёмности в задачу не входит.

Решение должно учитывать различия в ракурсах, освещении, типах кузовов и грузов. Среди грузов могут встречаться палеты, контейнеры, мешки и россыпь.

Обязательные функции
Распознавание загрузки. Приём фотографии и получение численного прогноза от 0 до 100%.
Привязка к перевозке. Сохранение результата вместе с номером перевозки и получение сохранённой оценки по этому номеру.
XML API. Доступ к обработке фотографии и получению результата через документированный программный интерфейс.
Обработка ошибок. Понятный ответ при передаче повреждённого или неподдерживаемого изображения.
Дообучение. Воспроизводимый способ повторного обучения или дообучения модели на новых фотографиях с подтверждённой разметкой.
В README опишите методы API, схему обмена, способ передачи фотографии и поведение сервиса при повторном обращении к одной перевозке. Адреса методов и структуру XML команда определяет самостоятельно.

Фотографии находятся в папках images. Имя изображения — <image_id>.jpg; сам идентификатор image_id записывается без расширения.

В train.csv используются колонки image_id,load_pct. В test.csv содержится только image_id: эталонные значения тестовой выборки скрыты.

Для локальной проверки разделяйте обучающие данные с учётом train_groups.csv: фотографии одной группы оставляйте в одной части разбиения. Группы сформированы по визуальному сходству и не являются подтверждёнными идентификаторами рейсов.

Baseline на NumPy и Pillow показывает полный путь от чтения изображений до формирования CSV. Он сравнивает Ridge-регрессию по простым признакам изображения с постоянным прогнозом. Используйте его как отправную точку для собственного решения.

Технические ограничения
Прогноз должен быть конечным числом в диапазоне [0, 100].
API сервиса должен использовать XML. Способ передачи изображения необходимо документировать.
Предоставьте исходный код, зависимости, обученную модель либо доступ к её весам, команды обучения и получения прогнозов.
Результаты должны быть воспроизводимы по инструкции команды.
Промышленное подключение к Max, FTP или производственному хранилищу, обработка видеопотока и автоматическое решение о выборе машины не входят в обязательный объём MVP.
Критерии оценки
Автоматическая оценка качества

Основная метрика — средняя абсолютная ошибка:

MAE = mean(abs(эталон − прогноз))

Она измеряется в процентных пунктах. Чем ниже MAE, тем лучше; идеальное значение — 0.

Из 307 тестовых изображений:

153 относятся к public-части — для текущего ML-рейтинга;
154 относятся к private-части — для итогового ML-рейтинга.
Все тестовые фотографии доступны командам, но принадлежность к частям скрыта. Один отправленный CSV используется для обеих оценок.

На своей локальной валидации дополнительно посчитайте долю прогнозов с абсолютной ошибкой не более 10 процентных пунктов. Это показатель достижения целевого качества заказчика; он не заменяет MAE и не является порогом допуска.

Экспертная оценка

Жюри рассматривает:

отклонение прогнозов от эталона и устойчивость на разных фотографиях;
наличие трёх базовых возможностей: распознавание, API и дообучение — по принципу реализовано / не реализовано;
скорость обработки фотографий и потока запросов с учётом оборудования;
дополнительные функции и их пользу для пользователей;
качество API, простоту интеграции и последующего обновления модели.
При проверке базовой функциональности учитываются качество API, простота интеграции и обновления модели. Экспертная оценка сервиса проводится отдельно от автоматического ML-рейтинга.
