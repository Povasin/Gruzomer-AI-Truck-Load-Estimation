## Основной вывод

В репозитории две разные архитектуры оценки загрузки и отдельные инструменты обучения сегментации:

1. **Текущий baseline:** сегментация кузова → вырезание области кузова → сегментация свободного пола → 277 числовых признаков → Ridge / HistGradientBoosting / медиана.
2. **CNN:** изображение → letterbox и аугментации → backbone timm → регрессия загрузки и две вспомогательные классификационные головы. Обучение по K-fold находится в отдельном скрипте.

Добавленный `src/model.py` реализует `TruckLoadNet`, поэтому замечание об отсутствующей архитектуре CNN больше не актуально. Однако CNN всё ещё не подключена к `baseline.py`, а отдельного `predict_cnn.py`, упомянутого в комментариях, нет.

Объединение возможно. Простого переноса файлов или переименования модели недостаточно: необходимо согласовать способ проверки качества, обработку изображений, формат модели и инференс. Уменьшение MAE после объединения без эксперимента не гарантируется.

## Что выполняет команда пользователя

Корректная запись в одну строку для PowerShell:

```powershell
python .\src\baseline.py train --model .\models\baselineV2.npz --errors-output .\models\baselineV2_errors.csv
```

Обратный апостроф в PowerShell нужен для переноса строки; обрамлять им аргументы не нужно. Для воспроизводимости окружения используйте существующий `venv`:

```powershell
.\venv\Scripts\python.exe .\src\baseline.py train --model .\models\unified_v1.npz --errors-output .\models\unified_v1_errors.csv
```

Второй пример показывает отдельные имена будущих результатов; он не запускался и пока выполняет существующий baseline, а не объединённую модель.

Фактическая цепочка:

```text
baseline.py train
  └─ train.py::train
       ├─ report.py: чтение и проверка фиксированного разбиения
       ├─ features.py: признаки train и validation
       │    ├─ segmentation/runtime.py: маска кузова
       │    │    └─ src/segmentation/models/best_unet_resnet18.pth
       │    ├─ bbox маски → область кузова
       │    ├─ floor_segmentation/runtime.py: маска свободного пола
       │    │    ├─ floor_segmentation/model.py: FloorUNet
       │    │    └─ floor_unet_resnet18_lr1e3.best_loss.pt
       │    └─ 235 базовых признаков + 42 признака пола = 277
       ├─ обучение Ridge и boosting; расчёт медианы
       ├─ оценка на validation; выбор метода
       ├─ запись CSV ошибок validation
       ├─ финальное обучение выбранного метода на train + validation
       └─ сохранение модели и JSON-отчёта
```

**Команда обучает регрессор загрузки, но не обучает сегментаторы.** Она использует уже существующие веса кузова и пола. Если веса пола отсутствуют, код молча переходит на цветовую эвристику. Если отсутствуют веса кузова, извлечение признаков завершается ошибкой.

`baseline.py` на уровне импортов загружает также `predict.py` и `submission.py`; при `train` функция записи конкурсного submission не выполняется. Для прогнозирования нужна отдельная команда `baseline.py predict`.

## Найденные проблемы

### 1. Можно получить прогноз другой модели, чем указана в команде — высокий приоритет

`src/predict.py:16` сначала проверяет соседний файл с расширением `.pkl`. Если он существует, указанный `.npz` вообще не загружается. `src/train.py:163` при выборе boosting сам меняет расширение выходного пути на `.pkl`.

Пример: сначала обучение сохранило `experiment.pkl`, затем Ridge сохранил `experiment.npz`. Прогноз с `--model experiment.npz` продолжит использовать старый `experiment.pkl`. Возможна путаница модели, JSON и CSV ошибок при повторном использовании одного имени.

Нужно загружать ровно указанный артефакт или использовать явный манифест, содержащий тип и путь модели. Фактический путь результата должен выводиться после обучения.

### 2. Модель не фиксирует версию обработки и веса сегментации — высокий приоритет

`src/features.py:17` задаёт 277 признаков. Актуальный отчёт `baselineV10.json` также описывает 277 признаков и метод boosting. Несовпадение размерности V10 с текущим кодом по отчёту не обнаружено; сам `.pkl` не загружался.

Однако совпадение размерности не подтверждает совпадение обработки изображения и весов сегментации.

В артефакте нет версии признаков, идентификаторов сегментаторов и конфигурации обработки. Текущее пользовательское изменение `best_iou.pt` → `best_loss.pt` меняет входные признаки без смены их размерности. Отдельная проблема — незаметный переход на эвристику пола при отсутствии `.pt`.

Нужно сохранять версию и порядок признаков, параметры обработки, используемые веса сегментаторов и режим пола. Несовместимость должна обнаруживаться до обработки изображений.

### 3. CNN не подключена к единой точке входа и не имеет завершённого инференса

`src/baseline.py:36` предлагает только `auto`, `ridge`, `boosting`, `median`. `src/train_cnn.py` запускается отдельно и пишет `foldK_best.pt`, историю и агрегированные MAE. `src/dataset.py:142` содержит `InferenceDataset`, но в исходниках нет её потребителя. `predict_cnn.py` отсутствует.

CNN не сохраняет CSV ошибок в формате baseline, индивидуальные OOF-прогнозы и `within_10_pct`. Для объединения потребуются общий CLI, общий вывод метрик, сохранение прогнозов validation и загрузчик CNN/гибридной модели. Добавлять только новый флаг недостаточно.

### 4. Сравнение качества пока неоднородно; разделение должно охватывать всю цепочку

Baseline оценивается на одном фиксированном split, CNN — средним MAE по фолдам. Числа нельзя напрямую сравнивать как результаты на одинаковых фотографиях. CNN усредняет MAE фолдов без взвешивания по их размеру; это может отличаться от общего MAE по всем OOF-прогнозам.

`src/segmentation/train_seg.py:124` использует обычный `train_test_split` списка размеченных фотографий без `group_id` и без согласования с validation регрессии. Поэтому код не гарантирует изоляцию оценочной выборки всей цепочки. Фактическое пересечение не проверялось из-за исключения DataSet и отсутствия происхождения весов.

Для пола `make_floor_split.py` уже учитывает фиксированные группы. Но при переносе этих весов в CNN K-fold некоторые оценочные фолды могут пересекаться с обучающей частью сегментатора. Это нужно проверять по происхождению весов; нельзя автоматически считать такие оценки независимыми.

Для первого сравнения следует использовать один фиксированный split для baseline, CNN и гибрида. Сохранённая финальная модель baseline обучена на train + validation: её повторная оценка на той же validation не является независимой.

### 5. Выбор метода делает лишнюю работу и нарушает правило ничьей

`src/train.py:114` и `:120` обучают Ridge и boosting независимо от `--method`. Даже `--method median` извлекает признаки двумя нейросетями, обучает оба регрессора и в конце ещё вычисляет финальный Ridge.

`src/train.py:132` при равном MAE выбирает boosting по порядку ключей словаря. В AGENTS.md оговорено предпочтение медианы при равенстве. Это подтверждено проверкой текущего выражения выбора.

Нужно выполнять только необходимые этапы для явно заданного метода и задать явное правило разрешения ничьей для `auto`.

### 6. CNN использует устаревшие параметры аугментаций

В `src/dataset.py:57`, `:88`, `:93` передаются `value`, `max_holes`, `max_height`, `max_width`, `fill_value`. В установленном Albumentations 2.0.8 соответствующие сигнатуры используют `fill`, `num_holes_range`, `hole_height_range`, `hole_width_range`.

Несовпадение подтверждено чтением кода установленного пакета. Заданные значения могут игнорироваться с предупреждением, поэтому фактические аугментации не соответствуют описанному эксперименту. Сами преобразования фотографий не запускались.

### 7. Воспроизводимость и входная валидация CNN недостаточны

- В `train_cnn.py` нет общего seed для Python, NumPy, PyTorch, DataLoader и аугментаций. Seed в `cv_split.py` фиксирует только разбиение.
- Готовый folds.csv читается в `train_cnn.py:244` без повторной проверки групп, уникальности и безопасности ID, диапазона цели и состава фолдов. Проверка в отдельном генераторе не защищает от изменённого CSV.
- Выбор несуществующего фолда или нулевые числа эпох не отклоняются заранее; возможны пустые выборки и checkpoint с `best_state=None`.
- `model.py:50` замораживает только градиенты. `train_cnn.py:48` снова включает `train()` для всей сети, включая BatchNorm backbone: статистики могут обновляться в «замороженной» фазе.
- Счётчик early stopping не сбрасывается при переходе фаз. При иных значениях patience/числа эпох остановка может произойти до полноценного дообучения backbone.
- Checkpoint CNN не содержит всей конфигурации обучения, разбиения и аугментаций. Фиксированные категории в `dataset.py` совпадают с категориями в сохранённом отчёте V10; актуальные CSV не проверялись.

### 8. `debug.py` действительно устарел; часть функций больше не используется

`src/debug.py:11` импортирует `_find_container_corners`, `_line_candidates`, `_normalized_container_image`, `_resize_for_detection`. В нынешнем `features.py` их нет. Скрипт не может выполнить свои функции даже при установленных зависимостях.

В остальных исходниках не найдены вызовы `train.py::predict_model` и `features.py::blue_ratio_from_rgb`; `DETECTION_MAX_SIDE` только объявлен. `dataset.py::InferenceDataset` тоже пока не вызывается, но полезна для будущего CNN-инференса.

В `floor_segmentation/prepare_floor_dataset.py` после `return selected` на строке 333 осталась недостижимая старая реализация выбора изображений.

### 9. Некоторые вспомогательные скрипты небезопасно импортировать

- `work_data.py` при импорте читает CSV, перебирает 5000 разбиений и записывает файлы.
- `segmentation/train_seg.py` при импорте читает изображения, создаёт сеть и запускает обучение.
- `segmentation/annotate.py` при импорте читает каталог изображений и запускает GUI.
- `floor_segmentation/prepare_floor_dataset.py` при импорте создаёт каталоги внутри DataSet.
- `floor_segmentation/annotate_floor.py` при импорте создаёт каталоги и получает список изображений.

Эти модули нельзя просто импортировать в будущую единую команду. Работа должна быть вынесена в функции, вызываемые явно из `main()`.

### 10. Пакетные импорты вспомогательных инструментов несогласованы

`floor_segmentation/check_floor.py:9` использует `from runtime import ...`, а сам runtime — `from floor_segmentation.model import ...`. При обычном прямом запуске из корня путь поиска начинается с `src/floor_segmentation`, где пакет `floor_segmentation` не находится; запуск как пакета, в свою очередь, не исправляет верхнеуровневый `runtime` автоматически.

`prepare_floor_dataset.py` аналогично требует доступности `src` для импорта `segmentation`. Эти сценарии зависят от рабочей директории/PYTHONPATH. Вывод сделан по импортам, полноценный запуск не выполнялся. В `check_floor.py:241` также найден SyntaxWarning из-за обратных слешей в строке с примером команды.

### 11. Защита CSV имеет пропуски

`report.py:67` проверяет уникальность `image_id` до удаления пробелов на строке 76. Два ID `same` и ` same ` проходят проверку, а затем становятся одинаковыми. Воспроизведено на временном CSV вне DataSet.

`submission.py:14` соединяет ID и прогнозы через обычный `zip`: короткий список прогнозов молча сокращает CSV, а сообщение всё равно выводит количество исходных ID. Воспроизведено: два ID и один прогноз дали одну строку с сообщением `Saved 2 predictions`.

После объединения веток особенно нужны проверки длины, конечности, диапазона и порядка прогнозов. Проверку ID следует выполнять после нормализации, с явной политикой допустимых имён.

### 12. Дублирование обработки изображения создаёт риск расхождения признаков

Логика crop присутствует в `features.py`, `prepare_floor_dataset.py` и `precrop_truck.py`. В первых двух bbox берётся по всем пикселям маски, в третьем — по крупнейшей компоненте с отступом. Это разные входы модели, а не взаимозаменяемые реализации.

`precrop_truck.py:87` проверяет площадь bbox (`bw * bh`), хотя описание обещает проверку площади самой компоненты. Тонкая разреженная компонента с большим bbox пройдёт этот порог.

Готовые изображения подготовки пола пропускаются по одному признаку существования файла. Смена сегментатора или crop не обновляет уже созданные изображения автоматически. Floor runtime использует фиксированные size=320 и threshold=0.5, не восстанавливая эти параметры из checkpoint, хотя обучение их сохраняет.

Нужен общий контракт обработки и учёт конфигурации при повторном использовании подготовленных данных. Перенос новой обрезки в старый baseline меняет признаки и требует нового обучения.

## Предлагаемое объединение: предмет следующего этапа

Есть три разных уровня объединения:

1. **Один CLI, два отдельных метода.** Самый небольшой объём изменений, удобный запуск и сравнение, но признаки и предсказания моделей не объединяются.
2. **Ансамбль предсказаний baseline и CNN.** Сохраняет архитектуры, но требует обученных весов обеих веток, согласованных validation-прогнозов и проверки веса смешивания. Сейчас веса/прогнозы CNN отсутствуют.
3. **Гибрид CNN + числовые признаки.** Backbone извлекает обучаемый вектор, который объединяется с 277 признаками текущего baseline перед головой регрессии. Это непосредственно использует оба подхода, но требует нового обучения и проверки качества.

Для заявленной цели предлагается рассмотреть третий вариант, сохранив отдельные baseline и CNN как контрольные методы. Это предложение по архитектуре, не реализованная возможность и не обещание MAE.

Предполагаемый поток одной команды:

```text
baseline.py train
  → проверка конфигурации, весов и фиксированного split
  → однократное извлечение/кэширование масок и числовых признаков
  → CNN-признаки изображения + нормализованные числовые признаки
  → общая голова регрессии; вспомогательные головы при обучении
  → MAE, within_10_pct и CSV ошибок на общей validation
  → финальное обучение по зафиксированному правилу
  → единый артефакт с конфигурацией и ссылками на необходимые веса
```

Числовые признаки нормализуются только по train при оценке. Идентичность обработки при обучении и predict обязательна. Сегментация выполняется вне эпох и DataLoader-воркеров, чтобы не повторять тяжёлые вычисления каждый раз. Кэш должен зависеть от изображения, версии признаков и весов сегментаторов.

Сохранить интерфейс `python src/baseline.py train --model ... --errors-output ...` возможно. Если требуется сохранить именно суффикс `.npz`, нужно заранее определить явный формат манифеста/контейнера: текущее `.npz` с коэффициентами Ridge не является готовым форматом CNN. Нельзя просто сохранять PyTorch/pickle под чужим расширением без соответствующего загрузчика и версии формата.

До реализации остаётся уточнить только факты исходного CNN-эксперимента: исходные или заранее обрезанные фото, backbone, параметры обучения, способ расчёта 9,6. Если их восстановить невозможно, объединение можно реализовать по имеющемуся коду, но его нельзя назвать воспроизведением результата друга.
