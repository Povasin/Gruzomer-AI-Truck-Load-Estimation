# Инструкции для работы с проектом

## Назначение и текущий объём

Проект оценивает загрузку грузового отсека по фотографии: целевая величина
`load_pct` — экспертная оценка заполнения в процентах, условно по занятой
площади пола. Это не оценка массы или грузоподъёмности.

Условия задачи находятся в `docs/info_hack.md`. Сейчас реализован CLI для
обучения и прогнозирования на NumPy и Pillow. XML API, хранение результатов
по номеру перевозки и сервисная обработка ошибок — требования к MVP, а не
уже реализованные возможности. Не описывай их как готовые без проверки кода.
README пока в основном содержит шаблон GitLab; актуальные параметры CLI
проверяй по `src/baseline.py` и его `--help`.

## Карта проекта

- `src/baseline.py` — точка входа CLI, команды `train` и `predict`.
- `src/features.py` — обработка EXIF-ориентации, преобразование в RGB и
  извлечение 233 признаков изображения.
- `src/train.py` — Ridge-регрессия, медианный прогноз, выбор по MAE,
  финальное обучение и сохранение модели с отчётом.
- `src/predict.py` — загрузка модели и получение прогнозов.
- `src/report.py` — чтение CSV, проверка разбиения и диагностика распределений.
- `src/submission.py` — запись CSV с прогнозами.
- `src/work_data.py` — отдельный скрипт подготовки группового разбиения.
- `DataSet/train/` — изображения, разметка, метаданные и готовые разбиения.
- `DataSet/test/` — изображения, `test.csv` и шаблон ответа.
- `models/` — модели `.npz` и отчёты `.json`.
- `output_csv/` — CSV с прогнозами.

## Окружение и запуск

Все команды ниже выполняются из корня репозитория в PowerShell.
Используй существующий рабочий Python из виртуального окружения; ниже
приведён путь `venv`. Если окружения нет, создай его через `python -m venv venv`.
Установка основных зависимостей:

```powershell
.\venv\Scripts\python.exe -m pip install -r requirements.txt
```

`requirements.txt` содержит NumPy и Pillow. Скрипт `work_data.py` дополнительно
использует `pandas` и `scikit-learn`, которых в этом файле пока нет. Если задача
затрагивает этот скрипт, обеспечь воспроизводимую установку этих зависимостей.
Не импортируй его для проверки: вычисления и запись файлов выполняются
на уровне модуля. Он читает `DataSet/train/train_metadata.csv`, перебирает
5000 вариантов разбиения и пишет `train_split.csv` и `validation_split.csv`
в текущую рабочую директорию. Не запускай его для обычного обучения по уже
готовому разбиению.

Обучение с отдельными именами выходных артефактов:

```powershell
.\venv\Scripts\python.exe .\src\baseline.py train `
  --train-split .\DataSet\train\train_split.csv `
  --validation-split .\DataSet\train\validation_split.csv `
  --images .\DataSet\train\images `
  --model .\models\baseline_check.npz `
  --alpha 100 `
  --method auto
```

Прогнозирование после этого обучения:

```powershell
.\venv\Scripts\python.exe .\src\baseline.py predict `
  --model .\models\baseline_check.npz `
  --test-csv .\DataSet\test\test.csv `
  --images .\DataSet\test\images `
  --output .\output_csv\submission_check.csv
```

Всегда передавай пути модели и результата явно: значения по умолчанию в CLI
содержат `../` и зависят от текущей директории. Модули используют локальные
импорты, поэтому запускай CLI как `python src/baseline.py`.

## Инварианты данных и обучения

- `image_id` хранится без расширения; файл изображения — `<image_id>.jpg`.
  Идентификаторы должны быть непустыми, уникальными и безопасными именами файлов.
- Исходный `train.csv` содержит `image_id,load_pct`, а `test.csv` — только
  `image_id`. Для текущего обучения нужны расширенные таблицы разбиения
  с колонками `image_id`, `load_pct`, `group_id`, `load_bin`, `vehicle_type`,
  `viewpoint`, `lighting`, `cargo_type`.
- Используй готовые `train_split.csv` и `validation_split.csv` без случайного
  переразбиения. Между ними не должно быть пересечений по `image_id` и
  `group_id`. Группы отражают визуальное сходство, а не подтверждённые рейсы.
- Нормализацию и параметры модели для оценки на validation вычисляй только
  по train. Не используй тестовые данные для обучения или подбора параметров.
- Основная метрика — MAE в процентных пунктах. Дополнительная —
  `within_10_pct`, процент прогнозов с абсолютной ошибкой не более 10 п.п.
- При `--method auto` сравниваются Ridge и медиана на фиксированной validation;
  при равном MAE выбирается медиана. После выбора финальная модель обучается
  на объединении train и validation. Не выдавай оценку этой финальной модели
  на той же validation за независимую проверку качества.
- Прогнозы должны быть конечными числами в `[0, 100]`. Выходной CSV имеет
  заголовок `image_id,load_pct`, порядок строк соответствует входному `test.csv`.
  Для конкурсного набора ожидаются 307 прогнозов; не зашивай это число в код.
- Сохраняй совместимость извлечения признаков при обучении и инференсе.
  При изменении состава или порядка признаков требуется переобучение либо
  явная версия формата модели. Загружай `.npz` с `allow_pickle=False`.

## Проверки изменений

В репозитории пока нет настроенных автоматических тестов, линтера и CI.
Не заявляй об их прохождении. Для изменений Python начни с проверки синтаксиса
и CLI:

```powershell
.\venv\Scripts\python.exe -m compileall -q src
.\venv\Scripts\python.exe .\src\baseline.py --help
.\venv\Scripts\python.exe .\src\baseline.py train --help
.\venv\Scripts\python.exe .\src\baseline.py predict --help
```

Для изменений ML-пайплайна выполни затронутые этапы с отдельными выходными
файлами. Проверь отсутствие пересечений разбиения, метрики в JSON-отчёте,
загрузку сохранённой модели, число и порядок строк CSV, отсутствие пропусков,
NaN/Inf и значений вне диапазона. При исправлении логики добавляй небольшие
проверки соответствующего поведения и граничных случаев; полный датасет
не должен быть обязательным для таких тестов. Изменения только документации
не требуют переобучения. Если данные или зависимости недоступны, явно укажи,
какие проверки не выполнены.

## Правила внесения изменений

- Общайся с пользователем и пиши проектную документацию по-русски.
  Следуй существующему стилю Python: четыре пробела, `snake_case`, `pathlib`,
  явная кодировка UTF-8 для текстовых файлов.
- Перед правками проверь `git status` и прочитай затронутые файлы, включая
  неотслеживаемые модули. Сохраняй чужие незакоммиченные изменения.
- Ограничивай правки поставленной задачей; не добавляй тяжёлые ML-фреймворки
  или веб-стек без необходимости. Новые зависимости фиксируй в проекте.
- Не добавляй в Git `DataSet/`, `env/`, `venv/`, `__pycache__/` и временные
  артефакты проверок. Первые три директории уже перечислены в `.gitignore`.
- Модели и CSV в репозитории могут быть отслеживаемыми файлами. Не перезаписывай
  готовые веса, отчёты и `submission.csv` при обычной проверке; используй
  отдельные пути. При намеренном обновлении весов сохраняй соответствующий
  отчёт и команду воспроизведения.
- При изменении CLI, схем данных или способа запуска обновляй документацию.
  При реализации сервиса соблюдай XML API и документируй передачу фотографии,
  номер перевозки, повторные запросы и ответы об ошибках.
- В итоговом ответе кратко перечисли изменения, выполненные проверки
  и оставшиеся ограничения; не приписывай модели непроверенные метрики.
